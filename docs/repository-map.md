# Карта репозиториев Heli

Что где лежит, кто чем владеет и где это работает. Документ только описывает; ничего не переносит и не удаляет.
Состояние на 07.11.2026. Обновлять в том же PR, где меняется владение, домен или путь на сервере.

## Правила (решение 07.11.2026)

- Всё по Heli bot (агент, клиенты, сервер бота, обучение) ведётся в проекте Claude «Heli bot» и в репозитории `x3-team/heli-bot`.
- Проект Claude «Getheli.ru» и репозиторий `x3-team/helicopter` — только сайт getheli.ru: оплата, баланс, акты, ЭДО, лендинги.
- Один PR на пункт.
- Ничего не удалять (ветки, файлы, deployment-файлы, данные на сервере), пока содержимое не перенесено и не проверено.
- Реальные аккаунты и балансы не трогать.
- Название треда Claude не доказывает, в каком репозитории должен лежать код. Смотреть на сами файлы.

## Репозитории

| Репозиторий | Видимость | Чем владеет | Чего здесь быть не должно |
|---|---|---|---|
| `x3-team/heli-bot` | публичный (desktop читает `releases/latest/download/latest.json` без токена) | Агент и его инструменты, сервер бота (FastAPI), облачный браузер, файловый мост, desktop (Tauri), веб-клиент, общий UI, evals, обезличенные учебные задания, деплой bot-api | Денежная логика и БД сайта, банковские реквизиты, сырые траектории, секреты |
| `x3-team/helicopter` | отдельный репозиторий сайта | Сайт getheli.ru: регистрация и вход сайта, баланс в рублях, оплата (Т-Банк и др.), акты, ЭДО, API моделей `/v1`, лендинг бота `getheli.ru/bot` | Код агента, коннекторы 1С/CRM, обучение бота |
| `x3-team/heli-bot-data` | приватный, создаётся | Оригиналы учебных материалов (папка `heli-bot-train`, 381 файл): задания, раннеры, грейдеры, отчёты, прогоны `runs*/*.jsonl`, fixtures; manifest с контрольными суммами и инструкция восстановления | Код продукта. Сюда не выкладывать файлы, не проверенные на ключи и пароли |

Почему учебные данные отдельно: в прогонах и fixtures (`mail-junior-v1.json`, `mail-hello-peek.json`, Ozon, `users*.py`) могут быть персональные данные и токены, а `heli-bot` публичный. Обезличенные копии заданий потом переносятся в `heli-bot/server/evals`, оригиналы остаются в `heli-bot-data`.

## Сервер pinvds (5.188.88.202)

Ubuntu 20.04, 2 CPU / 8 GB, 880 ₽ в месяц. На этом же хосте работает прод getheli.ru в `/opt/heli`: деплой бота его не трогает, и руками его тоже не трогать. Старый сервер Beget 212.67.13.64 мёртв после взлома, не использовать.

### Бот: `/opt/heli-bot`

| Путь | Что | В git? |
|---|---|---|
| `/opt/heli-bot/server` | Код сервера. Изначально скопирован вручную, это **не git checkout**; обновляется только через `deploy-pinvds` | Копия `server/` из git |
| `/opt/heli-bot/server/REVISION` | SHA и время сборки, которую выложил `deploy-pinvds` (видно в `GET /health` → `revision`; 07.11 сверено: прод = main `89d2263`) | Создаётся при деплое |
| `/opt/heli-bot/.env` | Секреты и настройки (`HELI_BASE_URL=https://getheli.ru/v1`, модель `heli-fast` и др.) | **Нет**, никогда |
| `/opt/heli-bot/server/var` | Рабочие данные при запуске из `server/`: SQLite по умолчанию (`sqlite:///./var/heli.db`), профили облачного браузера (`var/browser-profiles`), файлы моста (`var/files`) | **Нет**, никогда |
| `/opt/heli-bot/var` | Рабочие данные по старой схеме (`var/heli.db`); `deploy.sh` делает его копию в бэкап, если файл есть | **Нет**, никогда |
| `/opt/heli-bot/venv` | Python venv | Нет |
| `/opt/heli-bot/backups` | Бэкапы `server/` и `heli.db` перед каждым деплоем (последние 5) | Нет |
| `issue-cert.sh` на хосте | Ручной скрипт сертификата, в git его нет | Нет, перенести в runbook (пункт 6 плана) |
| systemd `heli-bot-api` | Сервис, пользователь `helibot`, слушает `127.0.0.1:8001`, перед ним nginx + Let's Encrypt | Шаблон: `infra/deploy/systemd-system` |

`deploy.sh` никогда не синхронизирует и не удаляет `server/var`, `var`, `.env`, `backups` и venv. Деплой только вручную: Actions → deploy-pinvds, сначала `mode = diff`, потом `deploy`, и только после согласия Vitalii.

Известные расхождения прода с git (аудит 07.11): `infra/deploy/ensure-open-access-in-env.sh` и `infra/deploy/env.venv.example` на хосте старые и всё ещё предлагают `HELI_OPEN_ACCESS=1`. Исправлено пунктом 6 плана: `deploy` обновляет `/opt/heli-bot/infra/deploy` из релиза (без удаления), `diff` показывает расхождения и скрипт `issue-cert` с маскировкой.

### Сайт: `/opt/heli` (только для справки, владелец — helicopter)

Сайт работает в Docker-контейнере `heli`; `/opt/heli/src` в контейнер не смонтирован и не показывает, что реально запущено. Данные сайта в volume `heli_heli-data`. CA для Т-Банка лежит вручную в `/opt/heli/orhop-ca.crt`. Всё это ведётся в проекте «Getheli.ru».

## Аккаунт, баланс и модели

- Сейчас у бота свои пользователи и свой учёт (`server/app/auth.py`, `server/app/quota.py`, цены в `server/app/llm/prices.py`). Модели бот вызывает через `getheli.ru/v1` одним серверным ключом `HELI_API_KEY`. Это общий API, но не общий кошелёк: расход пользователя бота не списывается с его баланса на getheli.
- Цель: общий аккаунт и баланс getheli. Сайт остаётся владельцем рублёвого баланса, бот работает через версионированный контракт (резерв, списание, возврат, в копейках). Контракт пишется в helicopter (пункт 4 плана), клиент к нему в heli-bot за выключенным флагом (пункт 5).
- **Открытый вопрос:** как связать баланс getheli и тарифы бота (Старт 390, Бизнес 1 490, Про 3 990 ₽ приняты как основа; дневные и месячные лимиты, перерасход с баланса getheli). Обсуждается в треде тарифов; до решения ничего в деньгах не менять.
- Модели (решение 07.11): Cloud.ru не используем, PR #49 закрыть без мержа. Позже свой открытый Qwen на нашем сервере (закрывает и 152-ФЗ), когда бот станет решать задачи. Сейчас для этого ничего не делаем, только держим слой провайдеров способным добавить OpenAI-совместимый endpoint.
